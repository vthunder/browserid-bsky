person signs into a browserid RP with their real Bluesky handle, an agent gets

## The demo, final agreed shape (web-first)

Decided after live testing showed the agent-first flow was awkward for the
write-consent step:

1. `browserid.me` links to a **dashboard at `bsky.browserid.me`**.
2. **Login = a handle text box** → uses browserid's **directed query**:
   `navigator.id.request({ provisionEmail: "<handle>@bsky.browserid.me" })`
   (verified: skips the chooser, authenticates that exact identity;
   include.js:803 / dialog.js:1717). **The dashboard MUST verify the returned
   presentation's identity equals what it asked for** — `provisionEmail`
   steers but does not bind. Secondary "or use any email" path → mint.
3. Dashboard branch: **create a local handle** (mint) OR **connect existing
   handle for write** (the write-relay: a *second* OAuth, `transition:generic`).
4. Dashboard shows a **personalized copy-paste prompt** with the grantor baked
   in (`<handle>@bsky.browserid.me`) — this structurally fixes the grantor-guess
   bug we hit (an agent pinned the user's email instead of the handle).
5. Agent's job shrinks to: request warrant (grantor pre-specified) + post.
6. Dashboard is also the manage/revoke surface.

## Key write-relay decisions (locked)

- **One OAuth implementation, hand-rolled** — NOT `atproto-oauth`. The crate
  has no resource-server/`createRecord` client (the one thing a relay needs)
  and drags 209 transitive crates. Identity flow's **structural zero-custody
  is untouched** (`exchange_code` returns only the DID, tests-locked); the
  write session uses *new sibling functions* in `relay/oauth.rs`.
- **Enforcement boundary:** `relay/mod.rs` `create_own_record` checks
  `collection` against `RELAY_COLLECTIONS` (const `[app.bsky.feed.post,
  me.browserid.warrant, me.browserid.provenance]`) *first*; `repo` is always
  `session.did` (not a parameter); reachable only from `attributed_post` after
  all existing warrant/attestation/scope/replay checks.
- **Connect crux:** stores a session only when OAuth `sub` == the DID pinned
  for the signed-in handle; allowlist + browser-binding + suspension re-checked
  at start AND callback.
- **Full provenance records written into the user's real repo** (not
  labeling-only) — required for independent `/verify`; consent must cover the
  clutter, records are the user's to delete. Verification + labeling are
  already repo-agnostic (verified).
- **Envelope-encrypt** the token columns (XChaCha20-Poly1305, per-column AAD
  `write_session:<did>:<column>`); **no whole-DB SQLCipher**. Missing key →
  **hard-fail at boot** (`WRITE_SESSION_KEY` hex/base64 32 bytes, or
  `WRITE_SESSION_KEY_FILE`).
- **Kill switch = warrant-revoke only.** Dropped the "disconnect the app at
  your PDS" second switch (that demos atproto's OAuth disconnect, not
  browserid). Warrant-revoke stops relayed posts transparently (checked before
  backend selection). Allowlist is also a live post-path gate.
- **Provenance fails loudly:** relay returns 502 `posted:true, attested:false`
  + URI + hint (not a silent 200) so the agent can tell the human.
- **Two bridge additions Phase 1 needed:** `/browserid/token` branches to
  resolve a connected grantor to their real DID (else bridge account, relay
  wins); new `GET /browserid/whoami` (bridge-token auth) so the agent learns
  the target DID before signing the attestation (`AttestationClaims.did` is in
  the signed bytes). `409 write_session_expired` tells the human to reconnect.

## Known gaps / watch-items (from the review, not blockers)

- Single-flight refresh lock is **in-process only** — a second bridge replica
  against one SQLite file could race a refresh (documented; single-process
  today).
- **No full end-to-end relayed-post test** (would need mock PDS + mock AS +
  real warrant/attestation bundle); pieces tested separately, seam by
  construction. The **first live claim is the real test** — most likely
  failure is the write-client metadata doc or the `transition:generic` grant.
- Blobs/images out of scope (text-only); no idle-session expiry sweep yet.
- Refresh-token lifetime is upstream-ambiguous (~90 days assumed); verify
  empirically before lifting the allowlist.
