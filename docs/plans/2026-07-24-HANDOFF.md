# browserid-bsky — session handoff (2026-07-24)

Continue the Bluesky bridge work. Everything below is **live in
production**, committed, and green. Nothing is half-built.

## TL;DR — what exists and works

A browserid-ng identity can provision a real Bluesky account and let a
warranted agent post to the live network, with **cryptographically
unforgeable, publicly verifiable provenance** and a **client-rendered
labeler** as the trust surface. Demonstrated end-to-end on bsky.app.

The one-liner value prop, proven live: *scoped, revocable, attributable
agent access to atproto that no other account can forge.*

## Architecture (how the bridge works)

- **`/browserid/provision`** — browserid login → creates the PDS account +
  binds grantor-email→DID. First-party only (grantee==grantor). Password
  shown once (see open bean `azxl`).
- **`/browserid/token`** — RFC 7521: four-object bundle → `bidb_` bearer
  token. **Verification is OUTSOURCED** to the hosted verifier
  (`POST {broker}/verify-access`) — one algorithm; the bridge is a plain RP.
  Token bound to {did, grantor, grantee, holder, scopes, warrant-status},
  1h TTL. Warrant status re-checked fail-closed on every use.
- **`/browserid/post`** — phase-2 attested post: grantee signs an
  attestation (access key), bridge verifies + reserves nonce (replay) +
  writes the post + provenance.
- **`/xrpc/*`** — bridge-token traffic is scope-enforced (allowlist) and
  repo-pinned, then forwarded with the account session; everything else
  passes through to the PDS. (No websocket/firehose passthrough yet.)
- **`/verify?uri=|n=`** — public receipt (HTML + `&format=json`); embeds the
  post; anti-spoof check. Resolves any did:plc.
- **`/.well-known/did.json` + `/xrpc/com.atproto.label.queryLabels`** — the
  labeler. Labels issue under the labeler *account* DID (`LABELER_DID`), and
  are `browserid-verified` (as-itself) or `browserid-on-behalf` (delegate).

Provenance records (bean 27c0, DONE): `me.browserid.warrant` (once per
warrant, deduped) + `me.browserid.provenance` (per post, {post, warrant-ref,
attributedTo=grantor, executedBy=grantee, nonce, attestation}). Lexicon doc:
`docs/lexicons/me.browserid.provenance.md`.

## Security boundary (important framing)

The in-post `🔗 verify` facet link is **convenience, not security** — a
malicious post can link to a fake verifier. The **labeler** (client-rendered
by bsky.app, keyed on the real post) is the trust surface; the paste-a-link
page is the manual fallback. See bean `4zx7`.

## Gotchas (all bit us this session)

- **DNS negative caching**: new subdomains NXDOMAIN-cache; use `BRIDGE_IP=`
  pin, or wait / flush. Records are all live now.
- **dokku = one cert bundle per app** → must be a SAN cert covering all the
  app's vhosts (broke pds.bsky when we installed a wildcard-only cert).
- **`CREATE TABLE IF NOT EXISTS` won't add columns** → store.rs has an
  idempotent `ALTER TABLE … ADD COLUMN` migration; add new columns there.
- **PDS expired session** = HTTP **400 `ExpiredToken`** (not 401); refresh
  on both, and update the LOCAL account copy after refresh (provenance
  writes use it).
- **The PDS has no SMTP** → flows that email a token (e.g.
  `identity.requestPlcOperationSignature`) return 200 but deliver nothing.
  Read the token from the PDS sqlite:
  `ssh dokku@sandmill.org enter bsky-pds -- node -p "eval(Buffer.from(\`<b64 js>\`,\`base64\`).toString())"`
  querying `email_token` in `/pds/account.sqlite` (better-sqlite3 lives under
  `/app/node_modules/.pnpm/node_modules/`). The dokku forced command **eats
  spaces and quotes** in args — hence base64 + backticks, which survive.
- **axum `Query` can't decode repeated params** (`uriPatterns`) → parse the
  raw query.
- **k256 0.14**: compressed pubkey via `verifying_key().to_sec1_bytes()`;
  `Signature::normalize_s()` returns a `Signature` (not Option).
- Verify locally before pushing: `cargo test -p pds-bridge` (14 tests) +
  `cargo build -p smoke`. Every push to main deploys.
